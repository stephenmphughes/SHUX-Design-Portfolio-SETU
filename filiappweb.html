Filí Web App

A full-stack Irish-language rhyming platform designed to support rhyme discovery, spelling accuracy, and playful learning through an interactive dictionary and two game modes.

Stack: React.js + Node.js / Express + SQL Server (Docker)

Overview

Designing a Rhyming Tool for Irish Language Learning

The Filí Web App was developed as a browser-based Irish-language rhyming tool that combines practical search with lightweight educational interaction. The aim was not only to let users find rhyming words quickly, but also to reinforce accurate spelling, including the correct use of fadas and Irish orthography.

From a product and UX perspective, the challenge was to make the experience feel forgiving without becoming vague. This led to a layered search model: the system first rewards correct spelling, then supports users through normalised matching, and finally offers a fuzzy recovery path when the word is close enough to be useful.

  • Core features: rhyming dictionary, spelling game, multiple-choice rhyme game, authentication, forum
  • Learning goal: support rhyme discovery while reinforcing correct Irish spelling
  • Technical goal: keep lookups fast and predictable through in-memory cache reads
Technologies

Full-Stack Build and Technical Choices

The application was built using a React front end, a Node.js / Express back end, and SQL Server running in Docker. This structure made it possible to separate interface logic from server-side rhyme processing while keeping authentication, forum functionality, and data persistence in one consistent system.

  • React.js: reusable front-end components and dynamic UI updates
  • React Router DOM: route handling and protected screens
  • Axios: client-side API communication
  • Node.js + Express: server routes and feature logic
  • SQL Server in Docker: structured persistence for users, words, rhyme groups, posts, and comments
  • mssql: parameterised database queries
  • Passport + bcrypt: authentication, password hashing, and login flow
  • express-session: persistent server-side sessions
  • NodeCache: in-memory read model for high-speed rhyme lookups
  • Fuzzball.js: fuzzy matching for dictionary recovery
  • Bootstrap: layout consistency and responsive structure
  • Teanglann integration: optional popup support for extra lexical reference
System Architecture

How the Application is Structured

The architecture was designed around a clear separation of concerns. React handles the interface and sends requests through Axios. Express routes requests into services and repository logic. SQL Server stores persistent data. For rhyme-heavy features, the application reads from a preloaded in-memory cache so that dictionary and game interactions remain fast and consistent.

Architecture Summary

The client sends requests to the Express API for authentication, dictionary search, games, and forum actions. On the server, feature logic is divided into controllers, services, and database access. SQL Server remains the source of truth, while NodeCache acts as the fast read layer for rhyme-related features.

  • Client: React SPA with route-based views
  • API: Express routes for auth, rhyme lookup, games, and forum
  • Read model: NodeCache loaded from the words table on server start
  • Persistence: SQL Server for users, rhyme data, posts, and comments
  • Admin/data maintenance: Azure Data Studio for schema and content management
Database Design

Entity Relationship Model

The database schema supports two main areas of the product: linguistic data and user interaction data. The linguistic side stores rhyme groups and word records, while the interaction side handles users, forum posts, and comments. RhymeGroups act as the structural anchor of the dictionary by linking related words through a shared group id.

Authentication

Hashing, Sessions, and Protected Routes

Authentication was intentionally designed to stay small and explicit. On sign-up, the server checks whether an account already exists, hashes the password with bcrypt, inserts the user into SQL Server, and attaches the new user id to the session. On login, the server retrieves the user by email, compares the plaintext password with the stored hash, and then restores the session if the credentials are correct. Logout destroys the session, while protected routes use a lightweight middleware check to block write actions when no active session exists.

Key Logic

RhymeCache.js as the Read Model

One of the most important technical decisions in the project was to use an in-memory cache as the main read model for rhyme-heavy features. When the server starts, it connects to SQL Server, loads the words table into memory, and then serves dictionary and game requests from cache rather than repeatedly querying the database. This keeps responses fast and predictable while SQL Server still remains the source of truth for persistent data.

The cache is preloaded from SQL Server when the server starts and then read through getCachedWords().

Why this mattered

The dictionary and both games are heavily read-oriented features. Without caching, the server would need to query the database on nearly every request. By preloading the word list into memory, the application gains faster and more predictable response times.

SQL Server still stores user accounts, forum content, and all rhyme data safely. The cache acts as a fast-access layer for lookups and game rounds, and can be refreshed whenever the underlying data changes.

  • Server start triggers one preload query
  • Dictionary and game routes read from memory, not DB
  • Faster lookups and fewer repeated database hits
  • SQL Server still handles persistence and system integrity
Language Logic

Diacritic and Orthography Normalisation

Irish spelling relies heavily on diacritics, particularly the fada. Because of this, the application needed a way to be strict enough to support learning, while still being forgiving enough to help users recover from minor input issues. The normalisation step removes accents from a word so that inputs such as Féar (grass) and Fear (man) can be compared in a shared form. This supports the middle stage between exact spelling and fuzzy matching.

Dictionary Logic

Three-Stage Rhyming Lookup Pipeline

The rhyming dictionary follows a three-stage cache-first pipeline designed to prioritise correct spelling while still offering useful recovery paths.

Exact stage: if the user’s query exists in its correct form, including fadas, the server reads its rhyme group and returns the full rhyming set.

Normalised stage: if no exact match exists, the query is normalised by removing diacritics and compared again. This catches close spelling attempts without treating them as fully exact.

Fuzzy stage: if neither of the first two stages succeeds, the query is compared against the normalised cache using a similarity score. If the best candidate passes a threshold, the app returns the candidate’s rhyme set and surfaces the closest suggested word.

Game Logic

Spelling Game: Exact Orthography with One Retry Path

The spelling game was designed to reinforce correct Irish spelling rather than simply rhyme recognition. For each round, the server selects a prompt from the in-memory cache only. It filters the data to ensure the chosen word belongs to a rhyme group with at least two members, so that each round has a valid answer space.

When a user submits an answer, the route trims both the given word and the user input, prevents reuse of the prompt itself, then finds the prompt’s group and compares the answer against valid rhyming entries.

  • First pass: exact canonical spelling including fadas
  • If matched: result is correct
  • Second pass on first attempt only: compare normalised forms
  • If matched here: result is retry
  • Otherwise: result is incorrect

Game Logic

Multiple-Choice Game: Rhyme Recognition from Cache

The multiple-choice game uses the cache for the full flow. The server selects a random prompt word, identifies its rhyme group, and gathers valid candidates from that same group, excluding the prompt itself.

One of those candidates becomes the correct answer. The server then scans the cached word list for entries belonging to different groups until it has collected three distractors.

The final four options are shuffled before being returned to the client. The user selects an option, receives immediate feedback, and the UI requests a new question.

Community Feature

Forum Posting and Session-Gated Database Writes

Unlike the dictionary and games, the forum was designed to read and write directly to SQL Server so that new content appears immediately. The API returns posts with author information and a live comment count through joins and subqueries rather than cached snapshots.

All create, edit, and delete actions require an authenticated user. This is enforced through the active session and through SQL-level owner checks. Updates and deletes only succeed when both the record id and the active user id match, preventing users from changing other people’s content.

  • Missing fields return 400
  • Unauthenticated requests return 401
  • Owner mismatch returns 404
  • Unexpected server issues return 500
Client-Side Forum Flow

On the front end, the forum component first loads posts and then retrieves comments per post. Users are given simple create, edit, and delete interactions with visible feedback. This keeps the feature intentionally straightforward and readable while still behaving like a real authenticated community layer.
